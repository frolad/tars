# End of the pipeline

What workshop-forge does once a pipeline's `iterations.md` is done, as `SKILL.md` says: the steps from the Done when check to the pipeline done.

The pipeline's record file says State built from then until step 7, and in progress while an iteration added by a step below runs.

1. Check the pipeline's Done when items, from the scope or from `iterations.md`, and the checks the scope's Risks name for it ("How we would notice"), against what was built: each one met, with where to see it, or not met. An unmet item becomes the next iteration, and the end of the pipeline stops there: the steps below wait until that iteration is done and the check passes.
2. When the project has a glossary or ADRs (`docs/GLOSSARY.md`, `docs/adrs/`, or its own equivalent), load workshop-glossary with the Skill tool and run its merge: the terms and decisions this pipeline built are proposed for the project's glossary and ADRs, each approved by the user. The proposals end the turn; once the user has answered and the approved entries are written, go on with the next step, so the commit takes them in. With nothing to propose, go on in the same turn. A project without them has not chosen to keep a glossary: skip this step without a word about it, and the Terms stay in the blueprint.
3. For code, announce the hardening phase: before the pipeline ends, its change can go through a cleanup, a code review of everything since the pipeline's `Base:` commit, and QA. A cleanup simplifies the changed code without changing what it does, such as Claude Code's simplify today. QA is checking the running software the way its users reach it, such as pages in a browser, API calls or an MCP server's tools; tests and reading the code are not QA. Build three picks from the kinds of skills the session lists at that moment: every kind it has, in the order cleanup, code review, QA, recommended; QA only; or no hardening. A skill of another kind that checks or improves the change joins the first pick, where it fits that order. Wait for the user's pick; an answer in other words, such as the code review alone, is taken as said. Each kind finds what the others miss, and the kinds decide, not the names: skills are added and renamed.
4. Cleanup, when picked, comes first: list the cleanup skills and run the pick like the review skills below. Its changes are an iteration of their own, reported and reviewed before the code review starts, so that the code review reads the cleaned code. Code review, when picked: suggest committing the pipeline's work first, since some review skills read only commits. The commit is the user's. Give the current condition: the range `<Base>..HEAD` and what is not committed yet. List the review skills you see in this session, numbered, with no recommendation: which one fits is the user's call, and the skills change. Run the one the user picks with the Skill tool; one you cannot invoke, the user types.
5. QA, when picked: after a code review, it starts once the fixes the user took from it are built, so that it checks the code that ships. List the QA skills you see in this session the same way, numbered, with no recommendation, and your own QA as one more pick after them, alone when the session lists none; run the pick the same way. A QA skill is any skill that checks the running software or tells how to start it and sign in to it, the repository's own, the user's own or a plugin's, whatever its description calls it. Your own QA, when picked: build the checks from the whole change since the Base commit, every place that shows what changed, in the ways its users reach it, and report what was checked and what was not. After QA's fixes are built, run the checks they touch again before the pipeline ends, since a check made before a fix is out of date.
6. The findings of the code review and of QA go through the light mode of workshop-grill, loaded with the Skill tool: check each one in the code, and a QA finding in the running software too, before it reaches the user, since a finding passed on unchecked can be wrong. One that does not hold is shown with what the code says, and asks nothing. Each one that holds is a decision of its own, numbered, with a recommendation, and each fix the user takes becomes an iteration, one fix each. Findings about code the pipeline did not change are shown apart, together, marked as not related to this pipeline, with one question for the group: fix the ones the user names, postpone them, or leave them as they are; the code review's and QA's each get their own. The code review runs once: its fixes are not reviewed again unless the user asks, since a review finds something new on every run.
7. The pipeline is done when every Done when item is met, the merge, if there was one, is answered, the hardening the user picked has run, and every finding is answered. The Current line says so, and the pipeline's record file says State done.
